## v2 — "killer engine" upgrade (same day, follow-up request)

After the like-for-like comparison snapshot above, the spec grew: negative
CLI arg = fixed depth, `0` = RAM-limited, and "hardest to beat ever".
The v1 numbers above are the honest apples-to-apples baseline; v2 is the
maximum-strength rewrite of the search/eval core (movegen and rules
untouched — perft re-passed 13/13 bit-identical):

- Parallel **Lazy SMP on all CPU cores**, lock-free XOR-validated shared TT
  (auto-sized to ~40% of available RAM, floor 64 MB / cap 16 GB,
  `CHESS_HASH_MB` override; measured 582% CPU on 8 vCPUs)
- Exactly **one limit per mode**: positive = seconds, negative = depth,
  `0` = RAM — thinks until the hash table is fully utilized, then moves
  (measured: 64 MB ≈ 4 s, 256 MB ≈ 17 s on 8 vCPUs — linear in RAM); Go
  runtime memory limit ⇒ can never OOM in any mode
- PVS + **aspiration windows** + **late move reductions** + adaptive
  null-move + reverse-futility/futility/late-move pruning + IIR +
  mate-distance pruning + check extensions
- Quiescence: **SEE** pruning, delta pruning, full check-evasion search
- Ordering: TT move, MVV-LVA, killers, **countermove**, history
- **PeSTO** tapered eval + bishop pair + passed/isolated/doubled pawns +
  rook (semi-)open files + king pawn-shield + tempo
- Upgrade wall time: **~35 min** (incl. full re-validation), ≈ 7K additional
  output tokens
- Spot checks: WAC.001 `Qg6!!` found in ≤ 5 s; mates-in-1 instant; K+Q vs K
  converted to mate without stalemate; full demo games to clean results at
  fixed-depth and timed modes

This feature set typically lands a single-file engine around strong-club /
master strength even at 1 s/move — far beyond casual human play — while v1
was a solid hobby baseline. Qwen's entry will be benchmarked against BOTH
(v1 for fairness, v2 for fun).

## v3 — match-validated SOTA pass (follow-up request, same session)

Request: "best chess ever possible, ≥4 passes, keep the modes, 0-mode at
80% of available RAM". Method: **match-driven development** — a referee
script plays the candidate against the previous binary from 10 fixed
openings (fresh process per move, threefold/50-move adjudication, Elo ±95%
CI); a pass only ships if it wins at real time controls, otherwise it is
reverted. A 16-position Win-At-Chess tactical sample and the 13/13 perft +
zobrist + pawn-key node-level verification gate every build.

| pass | features | verdict @1 s/move |
|---|---|---|
| 1 | new 24-byte TT (generation aging, 2-way buckets, depth-protected replacement, cached static evals), quiescence TT, continuation + capture history with gravity updates, improving flag, razoring, eval-scaled null-move R + verification search, history-driven LMR, persistent per-thread engines, 0-mode → 80% RAM (cap 64 GB) | **+70 Elo** (+11 =26 −3) |
| 2 | bitboard-assisted eval rewrite: mobility, king-safety attack units, threats/hanging men, passer blockade + king proximity, connected pawns, pawn hash table, OCB/pawnless drawishness scaling; verified mirror-symmetric | **+108 Elo** (+16 =20 −4) |
| 3 | incremental pawn zobrist (node-verified), **singular extensions + multicut**, **probcut**, **correction history**, SEE pruning of quiets and losing captures | **+44 Elo** over 80 games (+18 =54 −8) |
| 4 | adaptive stability-based time management — tested twice, no gain at 1 s (−17, −26) | **reverted** (binary byte-identical to pass 3) |

Chained per-pass gains sum to ≈ +220, and the independent headline match —
**final vs v2, 60 games at 1 s/move: +34 =19 −7, 72.5%, +168 Elo
[+79, +285]** — confirms a decisive upgrade. Fixed-depth
matches turned out to be the wrong metric — pass 1 measured −98 "Elo" at
fixed depth 5 while being +70 at equal wall clock, because the new pruning
reaches the same depth in ~8–26× fewer nodes; all verdicts above are
wall-clock time controls, the thing that actually matters.

Interesting engineering notes:
- The pass-1 "regression" hunt found one real bug the gauntlet exposed:
  quiescence depth-0 stores were overwriting deep same-key TT entries;
  fixed with depth-protected replacement (age-refresh instead).
- Correction history + pawn hash both key off a pawn zobrist that is
  maintained incrementally in make/unmake and re-verified against a
  from-scratch recomputation at every node of the perft suite.
- WAC tactical sample: 14/16 at 2 s/move (both misses are deep sacrifice
  lines; v2 scored the same 14/16 while being ~220 Elo weaker in play —
  tactics suites measure sharpness, not strength).
- v3 wall time: ~3.5 h of implement→race→bisect→revert loops, ≈ 25K
  additional output tokens.

| step | change | verdict @0.1 s/move |
|---|---|---|
| 1 | the same search, faster: packed moves, piece bitboards and material/piece-square sums kept incrementally, bitboard attacks, move generation (same move order), SEE (same choice of attackers) and evaluation (same values), per-ply move buffers | **+265 ± 25 Elo** (+568 =178 −54) over v3 |
| 2 | the whole time limit is used and an iteration cut off by the clock counts when it has found a better move (v3 stopped at 55-100% of the limit and threw the unfinished iteration away); threefold-repetition fix | **+45 ± 19 Elo** (+290 =323 −187) over step 1 |

| 4 | Lazy SMP: a helper thread goes on to the next depth when half of the threads already search one (they used to search the same depths side by side); the right corner for the bishop-and-knight mate (six test endings now mate in 25-39 moves, none did) | time to depth 17 with 8 and with 16 threads: −17%; 300 games with 8 threads each at 0.2 s/move: +8 ± 26 Elo (+68 =171 −61) - not significant by itself, kept for the time to depth |

How step 1 was checked: the search tree is the one of v3, node for node -
a fixed-depth search of 8 positions visits 2,720,148 nodes at depth 12 and

evaluation, attacked squares, move lists (order included) and the SEE of
10.2 million moves are equal. The staged ordering of step 3 gives the order
of the old one-pass sort on 185,196 move lists with random history tables.

What the audit found. The rules were tested against python-chess: 23,000
self-play games from random positions, 6,000 games against a random "human"
(legal moves, illegal ones and garbage) and 600 games played with the `c`
command; every move, every `check` and every result line was compared.
- Threefold repetition was declared late (4 of 23,000 games; none after the
  fix): the en passant square went into the position hash after every
  double pawn step, also when no capture was possible, so the first
  occurrence of such a position did not count.
- FreeBSD: the name of the "inactive memory" sysctl was misspelled, the
  program silently took half of the physical RAM for available and sized
  its hash table from that - 24.5 GB on a machine with 2 GB free.
- The hash table is now also no larger than a timed search can fill.
- GUI: the engine searched the very position the window was drawing (data
  race), every mouse button and the wheel acted as a click, the socket-path
  DISPLAY of XQuartz was not understood, a selected piece could not be put
  down again.
- Every hash store incremented one counter shared by all threads: 15% of
  the nodes/s at 16 threads (20.3M → 23.3M).

New in the repository: `chess_test.go` (GUI state machine, rendering,
command line, rules, memory sizing, search and - on a private Xvfb with the
real pointer - the program end to end on 24-, 16- and 8-bit displays) and a
`Makefile`. Tests and binaries were run on FreeBSD, Linux and macOS.

## v5 — a neural network evaluates, trained on its own games (2026-11-26)

Model: Claude Fable 5.2 (claude-fable-5.2) via GitHub Copilot CLI, one day
on the FreeBSD host, shared with other jobs, and four hours of an M1 Mac
for a quarter of the games, the last training and two matches. Requests:
"make it as smart/hard-to-beat as possible keeping current work modes"
and, on the way, "make sure it is not worse in any case than the current
version".

What changed:
- **Evaluation**: the hand-written evaluation (piece-square tables, pawn
  structure, mobility, king safety, threats) is gone. A network takes its
  place: for each side 768 inputs (own or enemy man, type, square, the
  board mirrored when that side's king is on the files e-h), 256 hidden
  units per side, one output with 8 sets of weights by the number of men
  and a value for every man.
- **Its arithmetic** is what a single Go file without assembly can do
  fast: hidden units are 16-bit lanes, four to a 64-bit word, stored with
  an offset so that whole-word additions update four units at once; the
  output takes 6 bits of each unit and 8-bit weights, and one 64-bit
  multiplication is the dot product of four units. Speed on one thread,
  80 positions to depth 11: 1.8M nodes/s against 2.1M with the
  hand-written evaluation on the FreeBSD host, 1.9M against 2.5M on the M1
  (a plain 16-bit loop would have halved it).
- **Its training** used nothing but the program: 649,825 games against
  itself (about 3,800 nodes a move, 80 hours of processor time), 57.7
  million positions, each with the score of its search and the result of
  its game. Four generations: v4 taught the first network, each network
  the next. The trainer is a Go program too (`nnue/`), half an hour for
  the last run. The weights are compiled in: the last 270 KB of
  `chess.go`, no file to carry around.
- **Where the network is not asked**: king and pawn against king is an
  exact table (111,282 won positions, built in 20 ms at startup); pieces
  against a bare king are scored by the known way to the mate; positions
  the network scores above 1000 are scored by material and progress, on
  one scale with the two before, so that a won game goes forward.
- **Search**: quiet moves that give check directly are never dropped by
  futility or late move pruning (+35 ± 16 Elo at 25,000 nodes a move, no
  difference found at 100,000; mates found in 290 forced-mate positions
  at depth 7: 204 instead of 131). The quiescence search knows the
  stalemate of a king with pawns at most. A position that has occurred
  once in the game is no longer a draw wherever the search meets it, only
  where the search ends; inside the tree it takes the third occurrence,
  or a repetition within the line searched.

What did not help, measured and dropped: quiet checks in the quiescence
search (more mates found, 48.8% in 607 games), more or less late move
reduction, a deeper null move, pruning margins a quarter tighter (43% in
259 games) or a quarter wider (−0 ± 20 Elo in 800), choosing quiet moves
one by one instead of sorting them (same tree, same speed), reading the
hash entry early (12% slower), damping the evaluation with the fifty-move
counter (the program then postpones its pawn moves to the end of every
line).

What "not worse in any case" turned up:
- The first networks won more slowly than v4 in a few elementary endings,
  and one version gave a rook away to reach king and pawn against king,
  which it knew exactly: positions known exactly, positions scored by the
  network and positions scored as won must lie on one scale.
- A mate in two went unseen at depth 10 because the mating move was a
  quiet move at a node that futility pruning had given up: the checks
  kept by the pruning.
- At depth 1 the program stalemated a bare king in 20 of 400 games (v4 in
  2): the quiescence search tries captures only and took the stalemate
  for a won position. None since it knows the stalemate.
- At depth 1 a king's step towards the bare king counted for more than a
  pawn's step to promotion: of the 150 won endings 5 were drawn, 2 now.
- Two games of rook against rook were lost at 0.1 s/move: the program
  went back into a position of the game "for the draw by repetition",
  where its opponent could simply take the rook, as it could have the
  first time. v4 does the same; the test positions came with an invented
  past of this kind, a human opponent makes one by overlooking a
  capture. The new rule for repetitions is neutral in ordinary games
  (−5 ± 20 Elo at 25,000 nodes a move, 800 games) and better in the
  balanced endings (+57 ± 12 instead of +52 ± 11 at depth 6). The
  stricter rule of other programs, the third occurrence for everything
  in the game's past, cost 16 of the 150 won endings at depth 1, where
  it is the old rule that keeps a shallow search from shuffling: so the
  old rule stays where the search ends.

New in the repository: `nnue/` (the four tools that made the network and
how to use them), tests of the network (word arithmetic against a plain
sum, move-by-move updates against a fresh computation, symmetries), of
the endings known exactly, of the checks, stalemates and repetitions.

### Follow-up the same evening: all cores, longer limits, how strong it is

Asked after the above: does the search use every core in every mode, is
the new program still the better one with 10 to 60 s a move, is the
network all of the evaluation, and how does it compare with engines
people know.

**Cores.** One search thread per CPU in all three modes, as before. CPU
time over wall time for one move from the start position:

| machine | time limit | depth limit | RAM mode |
|---|---|---|---|
| FreeBSD, 16 logical CPUs (8 cores) | 15.5 | 15.5 | 15.3 |
| macOS, M1, 8 CPUs (4 fast, 4 slow) | 7.5 | 7.5 | 7.4 |
| Linux, a virtual machine with 16 CPUs | 15.8 | 15.9 | 15.7 |

Half of these CPUs are hyperthreads on the FreeBSD machine and slow
cores on the M1. They add a third to the positions searched per second
(16.2M against 11.8M, 10.0M against 7.4M) and make the search wider, not
deeper: a fixed depth is reached no sooner (ten positions to depth 20 in
31 and 37 s with 16 threads, in 33 and 29 s with 8), and 16 threads
against 8 at 0.3 s a move ended +7 =10 −7. Nothing is lost by taking
every CPU; the gain is in the real cores.

One thing was wrong: the number of threads was the number of CPUs of the
machine, not the number the program may use. With 2 of 16 CPUs granted
(`GOMAXPROCS=2`, which is what a container with a CPU limit amounts to)
it ran 16 search threads on them and needed 6.0 s to depth 17 instead of
2.1 s. It now asks the Go runtime (`runtime.GOMAXPROCS(0)`); on Linux
under a real limit (`systemd-run --scope -p CPUQuota=200%`) it starts 2
threads.

In a virtual machine the count can be more than the host has to give.
The Linux guest of the table runs on the FreeBSD machine: with the host
idle it searched 12 million positions a second on its 16 CPUs; while the
host ran other work a search on all 16 threads crawled - a 3 s move took
20 s and saw 16,000 positions, where 12 threads saw 13 million - because
every first use of a page of memory then took milliseconds. The program
cannot see what a host has left; `CHESS_THREADS` is the remedy there.
