## v2 — "killer engine" upgrade (same day, follow-up request)

After the like-for-like comparison snapshot above, the spec grew: negative
CLI arg = fixed depth, `0` = RAM-limited, and "hardest to beat ever".
The v1 numbers above are the honest apples-to-apples baseline; v2 is the
maximum-strength rewrite of the search/eval core (movegen and rules
untouched — perft re-passed 13/13 bit-identical):

- Parallel **Lazy SMP on all CPU cores**, lock-free XOR-validated shared TT
  (auto-sized to ~40% of available RAM, floor 64 MB / cap 16 GB,
  `CHESS_HASH_MB` override; measured 582% CPU on 8 vCPUs)
- Exactly **one limit per mode**: positive = seconds, negative = depth,
  `0` = RAM — thinks until the hash table is fully utilized, then moves
  (measured: 64 MB ≈ 4 s, 256 MB ≈ 17 s on 8 vCPUs — linear in RAM); Go
  runtime memory limit ⇒ can never OOM in any mode
- PVS + **aspiration windows** + **late move reductions** + adaptive
  null-move + reverse-futility/futility/late-move pruning + IIR +
  mate-distance pruning + check extensions
- Quiescence: **SEE** pruning, delta pruning, full check-evasion search
- Ordering: TT move, MVV-LVA, killers, **countermove**, history
- **PeSTO** tapered eval + bishop pair + passed/isolated/doubled pawns +
  rook (semi-)open files + king pawn-shield + tempo
- Upgrade wall time: **~35 min** (incl. full re-validation), ≈ 7K additional
  output tokens
- Spot checks: WAC.001 `Qg6!!` found in ≤ 5 s; mates-in-1 instant; K+Q vs K
  converted to mate without stalemate; full demo games to clean results at
  fixed-depth and timed modes

This feature set typically lands a single-file engine around strong-club /
master strength even at 1 s/move — far beyond casual human play — while v1
was a solid hobby baseline. Qwen's entry will be benchmarked against BOTH
(v1 for fairness, v2 for fun).
